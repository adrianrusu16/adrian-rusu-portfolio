## The question

An automotive media experience crosses more boundaries than its interface reveals. A tap can become a playback request, a service call, a native state transition and a backend operation. Android also has lifecycle and playback state of its own to report.

> What if playback state, backend interaction and domain rules lived outside the Android UI process boundary?

PandaWave is my exploration of that question. Compose presents state. Android adapts platform capabilities. PandaEngine owns the client-side domain model.

## Architecture

<Diagram
  name="pandawave"
  alt="AAOS surfaces and Compose or Media3 call EngineGateway, across Binder/AIDL to MediaEngineService, then JNI/FFI to PandaEngine. The engine calls Canopy through canopy-api gRPC; Canopy owns PostgreSQL policy and authorized media delivery."
  caption="Different boundaries have different failure, lifetime and ownership semantics."
/>

| Layer             | Owns                                                  |
| ----------------- | ----------------------------------------------------- |
| Android / Compose | Presentation, lifecycle and AAOS integration          |
| Media3            | Platform playback execution and system media surfaces |
| Binder / AIDL     | The Android process boundary                          |
| JNI / FFI         | Kotlin ↔ Rust native transport                        |
| PandaEngine       | Client state and domain policy                        |
| canopy-api        | The canonical wire contract                           |
| Canopy            | Durable state, backend policy and media resolution    |

Binder/AIDL, JNI/FFI and gRPC are not interchangeable. The [native host contract](https://github.com/adrianrusu16/PandaWave/blob/master/docs/native-engine-host.md) spells out what each layer owns — and what must stay outside it.

## Intent is not observation.

PandaEngine owns what playback **should do**. Media3 reports what the platform **actually did**.

<Flow
  label="Playback request and observation loop"
  steps={[
    { title: 'User / system command', detail: 'Play, pause, seek or skip' },
    { title: 'PandaEngine', detail: 'Intent + queue policy' },
    { title: 'Typed playback effect', detail: 'Explicit platform work' },
    { title: 'Media3 / ExoPlayer', detail: 'Execute on Android' },
    { title: 'Observed player event', detail: 'Report actual state' },
    { title: 'PandaEngine → snapshot', detail: 'Update authoritative state' },
    { title: 'Compose + AAOS', detail: 'Project the same snapshot' },
  ]}
/>

> Each load carries an engine-created playback instance identity, allowing stale events from superseded loads to be rejected.

Media3 observations are therefore correlated with the active engine load instead of being treated as authoritative simply because they arrived last. The surrounding command/event loop is documented under [Playback ownership →](https://github.com/adrianrusu16/PandaWave/blob/master/docs/architecture-roadmap.md#playback-ownership).

The matched captures use the same emulator, theme, density and scroll position. Playback progress differs between the frames and is not an overlay effect.

`ResourceDesignTokenProvider` bridges Android resources into Compose. Public resource names let an OEM overlay adjust colors, spacing, typography, focus treatment and sizing without rewriting UI code. Runtime user themes remain an app preference; RRO is a platform customization boundary.

The [RRO guide](https://github.com/adrianrusu16/PandaWave/blob/master/docs/rro-guide/RRO_GUIDE.md) documents the inventory and a built, installed, enabled and rolled-back two-resource canary. That is a targeted contract validation, not a claim that every possible OEM overlay has been exercised.

## Performance questions

The useful artifact is a trace that answers a question. These are investigation areas and available tools, not published benchmark results.

| Area      | Question                                               | Evidence to inspect                                 |
| --------- | ------------------------------------------------------ | --------------------------------------------------- |
| Startup   | What is on the path to a usable surface?               | Macrobenchmark, Perfetto, startup sections          |
| Rendering | Which work misses a frame deadline?                    | Frame timeline, Compose/rendering traces            |
| Binder    | Where does process-boundary latency accumulate?        | ATrace / Perfetto slices and dispatch timing        |
| JNI       | Are unchanged values repeatedly crossing the boundary? | Native-host traces, metadata revision behavior      |
| Playback  | Where does request-to-observation time go?             | Engine effects, Media3 events and state transitions |

## Observability

Typed diagnostic events and redacted sinks make boundary failures inspectable without treating tokens, capability URLs, profile data or configuration as harmless log text. Diagnostics should explain state and timing while preserving the same ownership boundaries as the runtime.
